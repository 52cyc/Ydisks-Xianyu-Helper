# 外部货源协议接入指南

本文说明 Ydisks 闲鱼助手现有的卡速售 v2、卡易信 API 3.0 与蜜蜂汇云接入方式，并给出后续新增货源协议时可直接执行的开发清单。

> 重要限制：卡易信当前支持单规格卡密和单规格直充商品；`skuType != 0` 的多规格商品会在“校验商品”时明确拒绝。蜜蜂汇云第一版支持官方卡密卡券、返回卡券或兑换链接的餐饮商品、会员权益、话费/流量和游戏币直充；电影票、需要买家选择门店座位的餐饮代下单和油卡 CK 等多字段专用流程暂不作为通用直充保证。蜜蜂接口要求中国大陆出口 IP 且系统时钟误差不超过 30 秒。

## 快速配置

进入“货源管理 → 添加货源”，先选择协议，再填写对应身份字段。

| 协议 | 界面选项 | 商户字段 | 密钥字段 | 商品详情 | 下单 | 查单 |
| --- | --- | --- | --- | --- | --- | --- |
| 卡速售 v2 | `kasushou_v2` | UserId | API Key | `/api/v1/goods/info` | `/api/v1/order/buy` | `/api/v1/order/info` |
| 卡易信 API 3.0 | `kayixin_v3` | APP ID | AppSecret | `/api/v3/goods/getDetail` | `/api/v3/order/create` | `/api/v3/order/getDetail` |
| 蜜蜂汇云 | `mifeng_v1` | AppKey | AppSecret | `/api/merchant/productGoodsListNew` | `/api/merchant/upload_order` | `/api/merchant/order_info` |

站点地址必须填写供应商实际 API 根地址，例如 `https://supplier.example`，不要填写 Apifox 文档地址。密钥保存后会加密落库，接口和页面只返回“已配置”，不会返回明文。

配置完成后，在“自动化规则 → 付款后自动发货”中：

1. 发货来源选择“外部货源”。
2. 选择货源实例。
3. 输入远程商品 ID 并点击“校验商品”。
4. 校验成功后，系统每次都覆盖生成简化价格策略：利润率 `2.00%`、开启价格自动同步、开启价格倒挂停止采购。直充商品还要绑定校验结果返回的动态字段。
5. 保存并启用规则。

## 三套协议如何统一履约

系统不会把所有供应商逻辑写在一个客户端里。实例的 `provider` 决定路由到哪个协议适配器，适配器再把各家字段转换成统一模型。

| 统一含义 | 卡速售 v2 | 卡易信 API 3.0 | 蜜蜂汇云 |
| --- | --- | --- | --- |
| 商品 ID | `id` | `goodsId` | `miniunit_id` |
| 卡密商品类型 | `goods_type = 1` | `goodsType = 1` | `b_id = 13`；返回卡券或链接的餐饮商品为 `b_id = 18` |
| 直充商品类型 | `goods_type = 2` | `goodsType = 3` | 其他已支持 `b_id` |
| 采购数量 | `quantity` | `count` | `datas.num`（支持数量的业务） |
| 幂等外部单号 | `external_orderno` | `outerNumber` | `third_id` |
| 订单保护价 | `safe_price` | `safePrice` | `datas.maxAmount`（支持该字段的业务） |
| 直充字段 | JSON 对象 | `[{"name":"字段名","value":"字段值"}]` | `datas` JSON 对象 |
| 远程订单号 | `ordersn` | `orderNumber` | `order_id` |
| 卡号 / 卡密 | `card_no` / `card_password` | `cardNo` / `cardPwd` | `ys_cards[].card_no` / `card_pwd` |

自动化生成的外部单号格式为 `xy-{闲鱼订单号}-a{动作ID}`。首次请求前先写入本地履约订单；超时或结果不确定时，只按原外部单号查单。只有供应站明确返回“订单不存在”，系统才允许使用完全相同的外部单号重提，防止重复扣款。

### 统一订单状态

| 本地状态 | 卡速售状态 | 卡易信状态 | 蜜蜂状态 | 自动化行为 |
| --- | --- | --- | --- | --- |
| `unpaid` | `-1` | `0` | — | 不发货，进入持久化长轮询 |
| `waiting` | `1` | `1`、`7` | `1`、`11`、`12` | 不发货，进入持久化长轮询 |
| `processing` | `2` | `2`、`8`、`9` | `2` | 不发货，进入持久化长轮询 |
| `succeeded` | `3` | `3` | `3` | 发送卡密或直充结果，再确认闲鱼发货 |
| `failed` | — | — | `4`、`6` | 不重复采购，保留未发货并进入失败通知 |
| `cancelled` | `4` | `4` | — | 进入人工确认重试流程 |
| `refunded` | `5` | `5` | — | 进入人工确认重试流程 |

卡易信状态 `9` 表示退款处理中，不应提前当作采购成功，也不能发送卡密。

### 等待处理如何自动完成闲鱼发货

三种协议都把 `unpaid`、`waiting`、`processing` 视为“供应站已受理、结果尚未产生”。这不是普通执行失败，不占用普通自动化的三次失败重试上限。

系统把等待状态和下一次查询时间保存在数据库中，进程重启后仍能继续。每次查询都复用自动化首次生成的外部单号，不创建第二笔采购：

```text
首次等待后 1 分钟 → 2 分钟 → 3 分钟 → 5 分钟 → 之后每 10 分钟
```

长轮询最多执行 17 次，覆盖时间约两小时。实际查询由分钟级调度器领取，可能比目标时间晚不到一个扫描周期。

- 查到 `succeeded`：读取已经落库的卡密或直充结果，发送给闲鱼买家，然后继续执行确认闲鱼发货。
- 仍为 `unpaid`、`waiting`、`processing`：保存新的下次查询时间，不向买家发送未完成结果。
- 查到 `cancelled`、`refunded`：停止长轮询，进入人工确认重试流程。
- 约两小时仍未完成：出现在“自动化规则”的人工处理列表，可安全重试或终止。
- 账号暂时离线：仍可查询供应站；查到成功但闲鱼消息连接未就绪时，发送动作按原有安全重试恢复，不会重复采购。

升级兼容会自动识别旧版本中已经以三次普通重试耗尽的 `unpaid`、`waiting`、`processing` 记录，把它们转入长轮询并继续使用原外部单号。

## 卡速售 v2 协议

卡速售使用 13 位毫秒时间戳，请求头为 `Timestamp`、`UserId`、`Sign`。签名公式是：

```text
sha1(timestamp + bodyJson + apiKey)
```

`bodyJson` 必须与实际发送的 JSON 字节一致。现有实现使用同一份 `json.Marshal` 结果完成签名和发送。

卡速售直充字段保持对象形式。例如规则将字段 `1` 绑定到买家在聊天中确认的充值账号后，下单正文包含：

```json
{
  "id": 4994,
  "external_orderno": "xy-3316981548205025193-a1",
  "quantity": 1,
  "attach": {
    "1": "13800000000"
  }
}
```

智客属于卡速售 v2 兼容站，仍选择“卡速售 v2”，不需要单独写智客协议分支。

## 卡易信 API 3.0 协议

卡易信所有已接入接口均为 JSON `POST`。请求头包括：

| 请求头 | 值 |
| --- | --- |
| `X-APP-ID` | 商户 APP ID |
| `X-Version` | 固定 `3.0` |
| `X-Timestamp` | 10 位 Unix 秒时间戳 |
| `X-Signature` | 小写 MD5 签名 |

签名公式是：

```text
md5Lower(X-APP-ID + AppSecret + X-Version + X-Timestamp + bodyJson)
```

`bodyJson` 的编码、字段和值必须与真正发送的正文完全相同。不要先签名一个对象，再由另一段代码重新生成请求正文。

卡易信只在 `code = 1000` 时视为成功，其他业务码统一转换为错误；包含“订单不存在”或“未找到”的查单错误转换为系统稳定的 `ErrNotFound`，供安全重提逻辑判断。

### 校验商品

系统调用：

```json
POST /api/v3/goods/getDetail
{
  "goodsId": 4994
}
```

转换规则如下：

- `goodsType = 1` 转为卡密商品。
- `goodsType = 3` 转为直充商品。
- `salesPrice` 转为界面展示的采购价。
- `rechargeTemplates[].title` 同时作为规则字段 key 和卡易信下单 `attach[].name`。
- `regex` 转为统一校验表达式。
- `type = 13/14/15/16` 分别转为数字、下拉、多行、级联输入展示。
- `skuType != 0` 明确拒绝，防止当前规则没有保存 SKU 时误购默认规格。

例如商品要求“充值账号”，规则中配置的字段名称必须与详情返回标题一致：

```json
{
  "充值账号": "{chat_input}"
}
```

买家在聊天中回复账号并确认后，自动化把确认值转换成卡易信下单格式：

```json
{
  "goodsId": "4994",
  "count": 1,
  "notifyUrl": "",
  "outerNumber": "xy-3316981548205025193-a1",
  "safePrice": 2.8,
  "sku": "",
  "attach": [
    {
      "name": "充值账号",
      "value": "13800000000"
    }
  ]
}
```

这一流程不要求开启 AI。聊天采集、确认和重填是确定性状态机；AI 回复功能开关不会决定是否提交充值账号。

### 卡密和直充结果

卡密查单结果中的每张卡会整理成可直接发送的文本：

```text
卡号：NO-1
卡密：PWD-1
```

直充订单使用 `result` 作为统一充值结果。只有订单状态映射为 `succeeded` 后，自动化才会把结果发给买家并继续确认闲鱼发货。

## 蜜蜂汇云协议

蜜蜂汇云正式站点地址填写 `https://merchant.task.mf178.cn`，商户身份和密钥分别填写蜜蜂后台“开放平台 → API 对接”中的 AppKey 和 AppSecret。不要把 Apifox 文档地址填成站点地址。

蜜蜂所有已接入请求使用 JSON `POST`，公共参数为 `app_key`、`timestamp`和 `sign`。签名流程是：

```text
1. 取请求中除 sign、datas 以外的全部字段
2. 按 key 升序排列，空值字段也保留
3. 依次拼接 key + value
4. 末尾拼接 AppSecret
5. 计算小写 MD5
```

`datas` 会原样发送给蜜蜂，但不参与请求签名。时间戳只允许约 30 秒误差，部署机必须保持系统时钟同步。

### 校验商品和下单

“校验商品”会把输入的数字 ID 作为 `miniunit_id` 调用商品列表接口。系统使用 `goods_price` 作为实时采购价；`status != 1`、价格为空或价格小于等于零时拒绝采购和闲鱼价格同步。

会员、话费、流量和游戏币直充会生成 `target` 字段，可继续绑定 `{chat_input}`：

```json
{
  "target": "{chat_input}"
}
```

买家确认后的蜜蜂放单正文示例：

```json
{
  "app_key": "<AppKey>",
  "timestamp": "<Unix秒级时间戳>",
  "sign": "<MD5签名>",
  "miniunit_id": "1000033",
  "third_id": "xy-3316981548205025193-a1",
  "call_back_url": "",
  "datas": {
    "target": "13800000000",
    "maxAmount": 16.32
  }
}
```

`maxAmount` 只会传给文档明确支持该字段的业务。话费等未声明 `maxAmount` 的业务仍由本系统在远程下单前完成价格倒挂拦截。官方卡密、游戏币和餐饮类数量参数使用 `datas.num`，单次最多 10 份；其他直充业务当前一次只采购一份。`b_id = 18` 的餐饮卡券商品不收集 `datas.target`，履约成功后从 `ys_cards` 提取卡券或兑换链接。

### 查单和幂等恢复

蜜蜂返回 `code = 10010` 表示 `third_id` 已存在。系统不会换单号重买，而是调用订单列表查询原单。正常查单优先使用蜜蜂 `order_id`；还没有远程单号时，使用 `third_id` 和本地首次建单时间查询。

```text
建单后不满 60 秒：不请求蜜蜂查单接口
建单后 1-5 分钟返回 10015：仍保持 waiting，不重买
建单满 5 分钟仍返回 10015：确认原单不存在，才允许使用相同 third_id 安全重提
```

进程重启后仍从本地履约订单读取首次建单时间，不依赖内存计时器。这保证超时、断网和容器重启不会绕过 5 分钟幂等保护。

### 卡密和直充结果

蜜蜂状态 `3` 映射为 `succeeded`。`ys_cards` 中的普通卡号卡密、兑换码、链接和二维码地址会转换为可直接发给买家的文本。直充成功且没有卡密时发送“充值成功”，有 `voucher` 时同时发送凭证。

状态 `4`、`6` 统一映射为 `failed`，不自动创建替代采购单、不确认闲鱼发货。状态 `41` 保持 `unknown` 并继续原单核实，最终交给管理员处理。

## 保护价的协议差异

三种协议的保护价都用于阻止供应价异常时继续采购，但语义由供应站协议决定：

- 卡速售 v2：原样传递 `safe_price`。
- 卡易信 API 3.0：按文档传递订单总金额 `safePrice`，必须是 JSON 数字。
- 蜜蜂汇云：已支持的业务按文档传递订单总上限 `datas.maxAmount`；未支持该字段的业务只在本系统远程放单前拦截倒挂。

保护价不再要求商家手工填写。开启“价格倒挂停止采购”后，系统会按当前订单和动作自动生成订单总保护价；例如采购 2 件、该动作允许的总成本最多为 5.60 元，卡易信收到的是 `5.60`，而不是单件价格 `2.80`。供应站价格超过保护价时应返回业务失败，本系统不会发送卡密或确认闲鱼发货。

## 利润率、价格自动同步与倒挂保护

“付款后自动发货”规则中的每条外部货源发货内容只需要配置：

- `profit_rate`：售价相对实时采购价的利润率，例如 `2.00` 表示 2%。
- `price_sync_enabled`：是否自动同步价格。后台每 10 分钟检查全部已启用商品；只有按实时采购价和利润率计算出的新售价与当前闲鱼售价不一致时，才调用闲鱼改价接口。待付款订单仍按下单时的实时价格改价。
- `stop_purchase_on_inversion`：是否在闲鱼订单实付低于货源实时采购成本时停止采购。

开启后，系统收到闲鱼待付款卡片会先读取订单实际规格和数量，再匹配原付款发货规则并查询货源实时商品价：

```text
单个采购单位售价 = 货源实时单价 ×（1 + 利润率）
闲鱼目标总价 = Σ 单个采购单位售价 × 各动作实际采购数量
```

金额会向上取整到分。例如货源单价 `9.50`、利润率 `2.00%`，售价为 `9.69`。改价明确成功后，系统为本笔订单和每个采购动作保存独立报价快照，不修改规则全局配置。

付款采购时的动态保护价为：

```text
动作动态保护价 = 按利润率计算的动作售价
```

买家直接付款或订单改价未完成时，系统也会在创建任何货源订单前查询实时成本并做订单级倒挂校验：

```text
实时采购总成本 <= 闲鱼订单实付总额
```

如果开启倒挂保护且不满足，系统不调用采购接口、不创建货源订单、不确认闲鱼发货，而是立即按价格变化分支重新报价并引导买家退款后重拍。实时成本查询失败时也不会冒险采购，而是进入货源异常恢复流程。如果稳定外部单号已经存在，说明供应站可能已受理，恢复执行只查原单，不再重新做价格预检。

同一规格如果包含多条发货内容，必须全部是外部货源并全部开启价格自动同步，否则系统保持原价，避免只计算部分成本。多规格商品暂不直接修改商品页 SKU 价格，仍按买家订单的实际规格自动改价。货源商品价格为空、为 `-` 或当前不可购买时也不会改价。该功能与 AI 议价自动改价互斥。

### 买家询价、改价与履约通知

付款发货规则可以按商品配置咨询询价、改价成功、外部履约成功和采购最终失败通知，不影响普通本地卡密商品：

- `price_guidance_enabled`：买家咨询该商品时实时查询货源价；同一聊天会话 5 分钟内只成功报价一次，超过后的下一条咨询会重新查询。
- `price_query_prompt_text`：查询货源前先发送的等待提示。
- `price_guidance_text`：查询成功后发送当前报价和“需要时拍下但不要付款”的引导，支持 `{price_list}`；单规格还支持 `{price}`。
- `price_adjusted_notice_enabled` / `price_adjusted_notice_text`：系统读取实际规格和数量、查询货源最新价格并明确改价成功后，把最终订单金额发给买家。
- `fulfillment_success_notice_text`：外部采购开始前，系统按规则和订单防重发送固定的“已收到订单，正在发货”提示；采购成功后再发送这里配置的第二条完整消息。文案必须保留 `{delivery_content}`，系统会替换为真实卡密、兑换链接或直充结果，并支持 `{order_id}`、`{item_title}`、`{item_id}`、`{quantity}`。
- `fulfillment_failure_notice_enabled`：外部采购或查单在全部自动重试耗尽后，按失败类型向买家发送一次提示。
- `fulfillment_safe_price_notice_text`：供应站明确返回保护价拦截时，重新查询实时货源价并发送最新买家总价和重新下单引导。
- `fulfillment_failure_notice_text`：网络、接口、查单等货源站异常使用的人工核实提示。

推荐的查询前提示：

```text
亲，您好～正在为您查询当前最新价格，请稍候。
```

查询成功后推荐发送：

```text
当前最新报价：
{price_list}
如果需要，请先拍下但不要付款。系统会按您下单时的最新价格自动改价，确认金额后再付款。
```

咨询报价按购买一件闲鱼商品计算。单规格的 `{price_list}` 形如 `¥9.69`；多规格会按规则顺序生成 `30天：¥9.69`、`90天：¥18.80` 等逐行列表。同一规格配置多条外部发货内容时，系统会把这些内容按各自利润率和每件份数合并后报价。

如果任一待报价货源商品查询失败、价格无效或当前不可采购，系统不会发送虚假价格，本次记录会标记失败并允许后续买家消息重新查询。咨询报价只是即时参考；买家拍下后，系统仍会读取订单的实际规格和数量，再次查询货源价格并执行改价。

改价成功文案支持 `{price}`、`{quantity}`、`{item_title}`、`{item_id}` 和 `{order_id}`，例如：

```text
已按最新价格为您改价为 ¥{price}，请核对订单金额，确认无误后再付款。
```

消息投递使用独立防重记录：重复聊天消息不会反复查询和发送同一咨询报价，重复待付款卡片不会再次通知相同订单；发送失败、查询失败或进程异常留下的过期租约允许安全重试。只有闲鱼明确改价成功后才会发送最终价格，改价失败不会催促买家付款。

采购失败通知不会在供应站第一次报错或仍处于等待处理时提前发送。普通明确失败会先完成三次安全尝试，供应站 `waiting` / `processing` 状态则沿用后台长轮询；只有运行记录已经没有下一次自动恢复机会时才通知。同一规则、同一订单最多成功发送一次，订单继续保持未发货，原有管理员异常提醒不受影响。

价格倒挂或供应站保护价拦截必须归类为 `ErrSafePriceExceeded`，不能仅在自动化层模糊匹配所有错误文本。系统会按失败订单的实际规格、数量、实时货源价和利润率重新计算 `{price}`；查询失败、商品不可采购或规则未开启价格同步时，安全回退到货源站异常提示，不发送不可靠价格。

默认保护价拦截文案：

```text
您好，货源价格已发生变化，本次订单暂时无法按原价发货。当前最新价格为 ¥{price}。请先申请退款；如仍需要，请重新拍下但不要付款，系统会按最新价格为您改价。
```

默认货源站异常文案：

```text
您好，您的订单正在人工核实处理中，目前暂时无法自动发货。请先不要重复下单，我们会尽快处理。
```

失败文案支持 `{price}`、`{quantity}`、`{item_title}`、`{item_id}` 和 `{order_id}`。`{price}` 只在保护价分支提供最新买家总价；不要在文案中填写货源成本、采购保护价或利润。系统不会把供应商原始错误发送给买家，采购失败时仍不会发送卡密或自动确认闲鱼发货。

## 查看和重试订单

“货源管理 → 履约订单”保留：

- 外部单号：本系统幂等键。
- 远程单号：供应站订单号。
- 状态：统一状态。
- 结果：卡密数量、直充结果或最近错误。

普通处理中订单点击“查询状态”，只会查单，不会再采购。已取消、已退款或明确错误的订单，从“处理重试”进入自动化规则的安全重试流程；终态替代采购会创建 `-r2`、`-r3` 等新外部单号，避免复用供应站已经终结的订单。

“查询状态”不是等待订单自动完成的必需操作。后台长轮询查到成功后会自行恢复自动化；手动查询只是让管理者立即查看供应站最新状态。若订单已经超过约两小时进入人工处理，先查询到成功，再到“自动化规则”执行安全重试即可继续发结果和确认闲鱼发货。

## 后续新增协议的 AI 开发清单

下面的顺序适用于继续接入新供应商协议。

1. 先获取官方文档证据：鉴权公式、时间戳单位、成功码、商品详情、下单、按外部单号查单、订单状态、卡密和直充字段。不要根据相似系统猜字段。
2. 在 `internal/application/fulfillment/models.go` 添加新的 provider 常量；能复用统一模型时不要加入品牌字段。
3. 新建独立协议包，例如 `internal/vendorname/client.go`，实现 `fulfillment.Gateway`。
4. 签名和发送必须共用同一份 JSON 字节；HTTP 客户端必须由组合根注入，并限制超时和响应体大小。
5. 在货源组合根注册 provider，不要在已有任何品牌客户端里增加另一家协议判断。
6. 为不同数字状态提供明确的统一 `State`，不能假设所有供应商的 `0`、`1`、`9` 含义相同。只有真正的非终态才能映射为 `unpaid`、`waiting`、`processing` 并进入长轮询；保护价业务拒绝必须映射为 `ErrSafePriceExceeded`，供买家通知与普通站点异常分流。
7. 查单必须优先使用稳定外部单号；超时不能直接生成新单。只有明确查无订单才可同号重提。
8. 更新 `api/openapi.yaml` 的 provider 和状态枚举，再生成 `frontend/shared/api-contract/generated/schema.ts`，禁止手改生成文件。
9. 在货源管理页添加协议名称和动态凭证标签；协议密钥只允许写入，不允许回显。
10. 至少覆盖以下本地测试：准确签名、正文形状、商品转换、直充字段、卡密转换、每个订单状态、业务错误、查无订单、超大响应和不支持能力；还要证明非终态可按原外部单号重复查单，成功结果可供自动化继续发送。
11. 构建前端嵌入资源，并执行 Go、OpenAPI、前端类型、注释和架构门禁。
12. 文档中只放脱敏示例，不记录真实 APP ID、密钥、Cookie、文档密码或生产订单号。
